# Self-edit

Use this skill when the user asks you to change Warden's own source code.
It enforces a strict edit → build → restart loop and nothing else.

## Hard constraints

- **Only edit source.** You may create or modify files under exactly these roots:
  - `src/` — the orchestrator (compiled by `tsc` to `dist/`)
  - `container/agent-runner/src/` — the agent-runner (compiled to `dist/agent-runner`)
  - `voice/` — the voice + UI pipeline (NOT compiled — see *Which pipeline* below):
    `voice/ui/*.html` (the pywebview panels: chat, digest, ops/tasks, agents, …),
    `voice/voice/*.py` + `voice/core/*.py` + `voice/main.py` (STT/TTS/bridge), and
    `voice/run.sh` (the launcher).
- **Never touch anything else.** This includes `dist/` (build output), `data/`,
  `groups/`, `public/` (the web dashboard — a separate UI from the voice panels),
  `docs/`, `package.json`, `tsconfig.json`, the systemd unit file, `.env`, and any
  other config. If a change requires editing anything outside these source roots,
  **stop and tell the user what's needed** — do not do it yourself.
- **Never edit `dist/` by hand.** It is regenerated by the build. Always edit the
  `src/` (or `container/agent-runner/src/`) original and rebuild.

## Which pipeline?

Decide which pipeline the edit is in — they deploy differently:

- **Backend** (`src/`, `container/agent-runner/src/`) → compiled by `tsc`, needs
  `npm run build`, and `systemctl --user restart warden` to take effect. Follow
  the *Workflow* below. The restart kills this agent mid-turn — expected.
- **Voice & UI** (`voice/`) → NOT compiled. The HTML/CSS/JS panels and the Python
  voice modules run straight from source via the voice venv. No `npm run build`,
  and **do not restart warden** — the voice app is a separate local process
  (`voice/run.sh`, pywebview) that the warden service does not own, so restarting
  warden neither reloads the UI nor the voice code. Changes take effect on the
  next `voice/run.sh` launch. Follow *Voice & UI workflow* below.

## Workflow

Run these steps in order, from the project root (your shell cwd is already
`~/Projects/Warden`). Use your Bash/exec tool for every command.

1. **Make the edit.** Modify only files under `src/` or `container/agent-runner/src/`.
   Read the file first, then write the change. Keep edits minimal and idiomatic
   to the surrounding code.

2. **Build.** Run the full build (it compiles both source roots):
   ```
   npm run build
   ```
   Wait for it to finish and capture the exit code.

3. **Gate on the build.**
   - If the build **failed** (nonzero exit, TypeScript errors): **do not restart.**
     Report the exact compiler errors to the user and stop. Leave the source edit
     in place only if you intend to fix it next; otherwise revert it.
   - If the build **succeeded**: continue.

4. **Tell the user what's about to happen.** Send a message (via your normal
   send_message tool) stating what you changed, that the build succeeded, and
   that the service is restarting now so this session will end momentarily.
   Do this **before** step 5 — after the restart you will not be able to send
   anything because the restart kills the orchestrator and this agent with it.

5. **Restart the service.** Use the single canonical restart command — nothing
   else, no kill/start split, no sleeps, no extra steps that can race or fail:
   ```
   systemctl --user restart warden
   ```
   The restart kills the orchestrator and this agent with it; your turn will end
   abruptly. That is expected. The user's next message hits the freshly
   restarted instance running your rebuilt code.

After step 5, your turn ends abruptly — that is expected. The user's next
message will hit the freshly restarted instance running your rebuilt code.

## Voice & UI workflow

For edits under `voice/` only:

1. **Make the edit.** Modify the file(s) under `voice/` (e.g. `voice/ui/chat.html`,
   `voice/voice/tts.py`, `voice/run.sh`). Read first, keep edits minimal and
   idiomatic to the surrounding code.

2. **No build.** Voice/UI files are not compiled — skip `npm run build`. A Python
   syntax slip in the voice modules won't be caught by `tsc`; if you changed a
   `.py`, optionally sanity-check it with `python -c "import ast; ast.parse(open('FILE').read())"`.

3. **Do not restart warden.** The voice app runs as a separate process
   (`voice/run.sh`) that warden does not own. Restarting warden will NOT reload
   the voice UI and will kill this agent for nothing.

4. **Apply via a voice-app relaunch.** The change takes effect on the next
   `voice/run.sh` launch. Tell the user to relaunch it — or relaunch it yourself
   only if the user asked for the change to take effect now and a relaunch won't
   disrupt them (it closes and reopens the voice window).

5. **Report normally.** You did not restart warden, so your turn continues —
   confirm what you changed and that it applies on the next voice-app launch.

If a single task spans **both** pipelines (a backend change in `src/` plus a
voice/UI change in `voice/`), make the voice/UI edit first, then run the backend
build → restart-warden flow last, so the restart is the final act (after it, your
turn ends abruptly). Note in your pre-restart message that the voice/UI change
still needs a `run.sh` relaunch.

## Notes

- The running orchestrator executes `dist/index.js`; editing `src/` has no
  effect until you build and restart. Rebuilding overwrites `dist/` on disk but
  does not disturb the running process — safe to do while it runs.
- If the user only asked for a code change and did **not** ask to restart, still
  build (so the change compiles and errors are caught), but ask before running
  step 5. Apply the restart automatically only when the user asked for the change
  to take effect.
- If a build fails and you cannot fix it within one or two attempts, stop and
  report — do not loop on the build, and never restart on a failed build.
